Define System. Write its important terms.  4-Mark 2014 2015 2016 2017 2018+

Definition

A system is a group of interrelated components working together to achieve a common goal. It accepts input from the environment, processes it, and produces output with feedback control.

Basic Model

INPUT → PROCESS → OUTPUT → FEEDBACK
Example (ATM): Card+PIN → Verify → Cash+Receipt → SMS confirmation

Important Terms

  • Input: Data given to system
  • Process: Activities converting input to output
  • Output: Result produced
  • Feedback: Output used to improve system
  • Environment: External elements affecting system
  • Boundary: Limits separating system from environment
  • Subsystem: Smaller system within larger system

Conclusion

A system's effectiveness depends on proper integration of all components working towards a unified goal.
What is Prototype? Explain its types.  4-Mark 2014 2016 2018 2020 2024+

Definition

A prototype is a sample working model of the proposed system, created to understand user requirements and get feedback before building the final system.

Types of Prototype

  1. Throwaway Prototype: Built only for requirement gathering, then discarded. Used when requirements are unclear.
  2. Evolutionary Prototype: Continuously improved and eventually becomes the final system.

Example

Before building a mobile banking app, developers create a demo version showing the login and transaction screens to get user feedback — this is a throwaway prototype.

Benefits

  • Better understanding of requirements
  • Early user feedback
  • Reduces risk of project failure
  • Improves accuracy of final system

Conclusion

Prototyping bridges the gap between user expectations and final product by enabling early validation.

Explain Prototype and Joint Application Development (JAD) in detail.  12-Mark 2016 2017 2021 2022 2023+

Introduction

Two important modern approaches to system development are Prototyping and Joint Application Development (JAD), both emphasizing user involvement.

Prototype — Complete Explanation

A prototype is a sample model of the proposed system built before the actual system.

Prototype Process:
1. Identify Requirements → 2. Quick Design → 3. Build Prototype → 4. User Evaluation → 5. Refine Prototype → 6. Final System

Types:
• Throwaway Prototype: Used only for requirement gathering, then discarded
• Evolutionary Prototype: Improved continuously and becomes final system

Benefits: Better understanding | Early feedback | Reduces risk | Improves accuracy
Limitations: May create unrealistic expectations | Can become costly if too many iterations

JAD — Joint Application Development

JAD is a structured group approach where users, managers, and analysts work together in workshops to define requirements and design systems.

Components of JAD:
• Sponsor: Management representative who authorizes the JAD
• Facilitator: Leads the JAD sessions
• Users: Business users who define requirements
• Analysts: IT professionals who document and design

JAD Process: Planning → Session Preparation → Conducting Sessions → Documentation → Review

Comparison Table

BasisPrototypingJAD
ApproachBuild sample modelWorkshop sessions
User InvolvementThrough evaluationDirect participation
SpeedFast for simple systemsVery fast for complex
OutputWorking prototypeRequirements document
Best ForUnclear requirementsComplex organizational systems

Conclusion

Both Prototyping and JAD increase user involvement, reduce misunderstandings, and lead to more successful system implementations.

What is SDLC? List its phases. (VVI Q3)  4-Mark 2014 2015 2016 2017 2018 2019 2021 2022 2025+

Definition

SDLC (System Development Life Cycle) is a structured process used to design, develop, implement and maintain information systems. It provides a framework to build quality systems within budget and time.

7 Phases of SDLC (P-A-D-T-I-M)

  1. Project Identification & Selection: Identify problems and opportunities
  2. Project Initiation & Planning: Define scope, plan schedule and resources
  3. Analysis: Study current system, gather requirements, prepare SRS
  4. Logical Design: Design DFD, ER diagrams (technology-independent)
  5. Physical Design: Design database, file structures (technology-specific)
  6. Implementation: Develop, test, install, train users, go live
  7. Maintenance: Correct, adapt, improve and prevent problems

Memory Trick

P-A-D-T-I-M: Planning → Analysis → Design → Testing/Implementation → Maintenance

Conclusion

SDLC ensures systematic, disciplined approach to system development, reducing risks and ensuring quality.

What do you mean by Process Model? Describe Waterfall, Iterative and Spiral Model. (VVI Q9)  12-Mark 2019 2021 2022 2023 2025+

Introduction

A Process Model (also called Software Development Model or SDLC Model) provides a structured framework that defines the processes, activities and tasks used to build a software system.

1. Waterfall Model

The Waterfall Model is a sequential, linear software development approach where each phase must be completed before the next one begins.

Phases: Requirements → System Design → Implementation → Testing → Deployment → Maintenance

Characteristics:
• Each phase has specific deliverables
• No going back to previous phase
• Simple and easy to understand
• Documentation-driven

Advantages: Simple, clear phases | Easy to manage | Good documentation
Disadvantages: Inflexible | Working software delivered very late | Not suitable for changing requirements
Best for: Projects with clear, fixed requirements

2. Iterative/Incremental Model

The Iterative Model divides the project into small iterations (cycles), each producing a working version of the software that is incrementally improved.

Process: Initial Plan → Iteration 1 (Requirements→Design→Code→Test) → Evaluation → Iteration 2 → ... → Final Product

Characteristics:
• System built in small increments
• Each iteration adds new functionality
• User feedback incorporated after each iteration
• Risk identified early

Advantages: Early working software | Flexible | Risk reduction | User feedback
Disadvantages: Requires skilled management | Not all requirements known upfront
Best for: Large projects with evolving requirements

3. Spiral Model

The Spiral Model is a risk-driven process model that combines the features of prototyping and waterfall model, with emphasis on risk analysis.

4 Quadrants of each spiral:
1. Planning: Determine objectives, alternatives, constraints
2. Risk Analysis: Evaluate alternatives, identify and resolve risks
3. Engineering: Develop and test the product
4. Evaluation: Customer evaluation and planning for next spiral

Advantages: Risk handling | Suitable for large projects | User feedback at each spiral
Disadvantages: Costly | Complex | Requires risk expertise
Best for: High-risk, large, complex projects

Comparison Table

BasisWaterfallIterativeSpiral
ApproachSequentialCyclic/IncrementalRisk-driven cycles
FlexibilityRigidModerateHigh
User InvolvementMainly at startEach iterationEach spiral
Risk ManagementPoorModerateExcellent
Best ForFixed requirementsEvolving requirementsLarge, complex, high-risk

Conclusion

Each process model has its strengths. Waterfall for simple projects, Iterative for medium complexity, Spiral for large risk-intensive projects. The choice depends on project requirements, team size, and risk factors.

What is SRS? Write its contents and importance.  4-Mark 2014 2015 2017 2020 2021 2023+

Definition

SRS (System Requirements Specification) is a document that describes what the system should do. It acts as a contract between users and developers, defining all functional and non-functional requirements.

Contents of SRS

  1. Introduction (purpose, scope, definitions)
  2. Overall description of system
  3. Functional requirements (what system must do)
  4. Non-functional requirements (performance, security, reliability)
  5. Constraints (hardware, software, budget)
  6. External interfaces (user, hardware, software interfaces)
  7. Acceptance criteria

Importance

  • Acts as a contract between users and developers
  • Basis for design, development and testing
  • Reduces misunderstandings
  • Helps in change management
  • Used by testers to verify system

Memory Trick

SRS = WHAT (What the system should do). Standard: IEEE 830

Feasibility study is one of the most critical activities in system planning. It determines whether the proposed system is practical, economical, legally compliant, and operationally viable before committing major resources.

Maintenance CostBetter Control and Decision Making

Describe Coupling & Cohesion Design Principles. (VVI Q4)  4-Mark 2015 2016 2017 2021 2022 2023 2025+

Design Principle

In modular design, Coupling and Cohesion are the two most important design principles that determine the quality of a modular system design.

Coupling (Between Modules) — Low is GOOD

Coupling = degree of interdependence BETWEEN modules.
Goal: Minimize coupling (low coupling = good design)

Types (Low to High):
1. Data Coupling (Best): Modules share only simple data parameters
2. Stamp Coupling: Modules share composite data (entire records)
3. Control Coupling: One module passes control information to another
4. Common Coupling: Modules share global data
5. Content Coupling (Worst): One module uses internal data of another

Cohesion (Within Module) — High is GOOD

Cohesion = degree to which elements WITHIN a module are related.
Goal: Maximize cohesion (high cohesion = good design)

Types (Low to High):
1. Coincidental (Worst): No relation between elements
2. Logical: Grouped by category
3. Temporal: Executed at same time
4. Procedural: Follow a sequence
5. Communicational: Operate on same data
6. Sequential: Output of one is input to next
7. Functional (Best): Single well-defined function

Memory Trick

Coupling: Low = Good (like D-S-C-E-C-C, Data is best, Content is worst)
Cohesion: High = Good (Functional is best, Coincidental is worst)

Definition

Top-Down and Bottom-Up are two fundamental approaches to system/software design that define how modules are organized and developed.

Top-Down Design

Definition: Start from the whole system and break it down into smaller sub-modules until the lowest level is reached.

Process: System → Modules A, B, C → Sub-modules A1, A2, B1, B2

Advantages: Easy to manage | Provides overall view | Better control
Disadvantages: Detailed problems found late | Lower-level issues not addressed early

Bottom-Up Design

Process: Sub-modules → Modules → Complete System

Disadvantages: Overall picture hard to see initially | Integration issues may appear late
Used in: When existing modules are to be reused

FocusOverall structure firstDetails first
AdvantageEasy control & managementEnsures lower-level reliability
TestingIntegration test firstUnit test first

In practice, a Hybrid Approach combining both Top-Down and Bottom-Up is most effective for large system development.

Introduction

A Data Flow Diagram (DFD) is a graphical representation showing how data flows within an information system. It illustrates the movement of data from external entities through processes to data stores and vice versa.

DFD Symbols

SymbolShapeMeaningExample
External EntityRectangle / SquareSource or destination of data (outside system)Customer, Bank, Government
ProcessCircle / Oval (Rounded box)Transforms input data into outputValidate Order, Calculate Tax
Data StoreOpen rectangle (two parallel lines)Stores data — database, fileCustomer DB, Order File
Data FlowArrow with labelDirection and name of data movementOrder Details, Payment Info

Levels of DFD

Level 0 — Context Diagram (Highest Level):
• Shows the entire system as ONE single process/circle

• Expands Level 0 into major sub-processes (processes are numbered 1, 2, 3...)

• Further expands each Level 1 process into sub-processes
• Processes numbered as 1.1, 1.2, 1.3 (sub-processes of Process 1)

Describe Coupling & Cohesion Design Principles in detail with types. (VVI Q4)  12-Mark 2015 2016 2017 2021 2022 2023 2025+

Introduction

Coupling and Cohesion are fundamental design principles in modular programming that measure the quality of system design. They guide developers to create maintainable, testable, and reusable modules.

COUPLING — Definition & Types

Coupling is the degree of interdependence between modules. Low coupling = Good Design (modules are independent and can be modified easily).

TypeDescriptionExampleLevel
Data Coupling (BEST)Modules share only simple data parameters — no unnecessary sharingFunction A passes 'salary' value to Function BLOWEST (Best)
Stamp CouplingModules pass composite data (entire record/structure, though only part is used)Passing entire 'Employee' object when only name is neededLow
Control CouplingOne module passes control information (flags/codes) telling another what to doModule A passes 'mode=1' to Module B to decide operationMedium
External CouplingModules depend on external devices, formats, or communication protocolsTwo modules sharing a common external file formatMedium-High
Common CouplingModules share global data variables — changes affect all modulesAll modules reading/writing a global variable 'totalSales'High
Content Coupling (WORST)One module directly accesses or modifies internal data/code of anotherModule A directly changes the local variable of Module BHIGHEST (Worst)

COHESION — Definition & Types

Cohesion is the degree to which elements inside a module are related to each other. High cohesion = Good Design (module does one well-defined task).

TypeDescriptionExampleLevel
Functional (BEST)All elements contribute to a single, well-defined taskModule 'Calculate Tax' does only tax calculationHIGHEST (Best)
SequentialOutput of one element is input to the nextProcess → Validate → Calculate → Format (all related)High
CommunicationalAll elements operate on the same input data or produce same outputAll operations on 'Customer Record' in one moduleMedium-High
ProceduralElements follow a specific sequence of executionRead file, process data, write file — must be in orderMedium
TemporalElements executed at the same time (not functionally related)Module that initializes variables, opens files, and sets clockLow
LogicalElements perform similar functions grouped together arbitrarilyModule with all input routines grouped togetherVery Low
Coincidental (WORST)No meaningful relationship between elements in moduleRandom collection of unrelated functions in one moduleLOWEST (Worst)

Why Low Coupling + High Cohesion?

  • Easier Maintenance: Changes in one module don't cascade to others
  • Better Testability: Independent modules are easier to test
  • Higher Reusability: Well-focused modules can be reused
  • Improved Readability: Clear module responsibilities

Memory Tricks & Conclusion

Coupling (Low to High): D-S-C-E-C-C (Data, Stamp, Control, External, Common, Content)
Cohesion (High to Low): F-S-C-P-T-L-C (Functional, Sequential, Communicational, Procedural, Temporal, Logical, Coincidental)

Goal: Low Coupling + High Cohesion = Best Module Design
Explain Top-Down and Bottom-Up Design with comparison. Also explain Design Principles. (VVI Q5 & Q10)  12-Mark 2014 2016 2018 2021 2022 2023 2025+

Introduction

Modular and structured design principles guide the decomposition and organization of a system into manageable modules. The fundamental design approaches are Top-Down and Bottom-Up, supported by key design principles.

TOP-DOWN DESIGN — Complete Explanation

Definition: Top-Down Design starts from the overall system and progressively breaks it down into smaller, more detailed sub-systems and modules until the lowest level of detail is reached.

Process:
1. Start with the main system as a single module
2. Break it into major sub-systems
3. Further break each sub-system into smaller modules
4. Continue until each module performs a single function

Diagram:
System → Module A, Module B, Module C → A1, A2, B1, B2, C1, C2

Advantages:
  • Provides overall view of system first
  • Easy to manage and control
  • Better communication with management
  • Early identification of major components
  • Good for new system development

Disadvantages:
  • Detailed problems found late in development
  • Lower-level design issues not addressed early

BOTTOM-UP DESIGN — Complete Explanation

Definition: Bottom-Up Design starts from the most detailed, lowest-level modules and progressively combines them to build larger systems.

Process:
1. Identify and design lowest-level modules
2. Test and verify each module independently
3. Combine related modules into larger sub-systems
4. Continue combining until complete system is formed

Diagram:
Small Modules → Sub-systems → Complete System

Advantages:
  • Lower-level reliability ensured early
  • Modules can be reused in other systems
  • Unit testing done at each level
  • Best when existing modules can be reused

Disadvantages:
  • Overall system picture hard to see initially
  • Integration problems may appear late

DESIGN PRINCIPLES (VVI Q10)

PrincipleDefinitionBenefit
Simplicity (KISS)Keep design as simple as possibleEasy to understand, test and maintain
ModularityDivide system into independent, manageable modulesEasy maintenance, testing, and parallel development
AbstractionFocus on essential characteristics, hide detailsReduces complexity
Information HidingInternal details of a module hidden from othersReduces coupling, easier to change implementation
High CohesionElements within module are closely relatedModule does one clear task well
Low CouplingMinimize dependencies between modulesModules can be changed independently

Conclusion

In practice, both approaches are combined in a Hybrid approach for large system development. Top-Down provides the big picture and architecture, while Bottom-Up ensures reliable, reusable lower-level components. Good design principles like modularity, high cohesion, low coupling, and information hiding are always applied regardless of approach.
