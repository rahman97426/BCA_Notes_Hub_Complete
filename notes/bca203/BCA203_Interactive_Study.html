📘 Definition: A Real-Time System is one that processes input and produces output within a strict time deadline. Missing the deadline results in system failure or performance degradation.

Types of Real-Time Systems:

FeatureHard RTSSoft RTS
Deadline MissCATASTROPHIC failurePerformance degrades only
ExampleAircraft, Pacemaker, Nuclear reactorVideo streaming, Online gaming, UPI
ToleranceZERO delay allowedSome delay acceptable
✅ Conclusion: Hard RTS = Hazardous if late. Soft RTS = Slight delay Survivable.
📘 Definition: Prototype is an early working model of the system built quickly to gather user feedback BEFORE full development begins.

Types:

  1. Throwaway Prototype: Built to understand requirements → then DISCARDED. Final system built fresh.
  2. Evolutionary Prototype: Built → improved repeatedly → BECOMES the final system.

Advantages:

  • User sees system early → misunderstandings reduced
  • Errors found cheaply before full investment
  • Higher user satisfaction
  • Shorter overall development time
✅ Conclusion: Prototype = Preview before Production! Reduces risk of building wrong system.
📘 Definition: A System is a set of interrelated components working together to achieve a common goal. It accepts input from the environment, processes it, and produces output with feedback for control.
Formula: INPUT → PROCESS → OUTPUT → FEEDBACK
📐 Basic System Model:
Card + PIN (Input) → Bank verification (Process) → Cash dispensed (Output) → Wrong PIN error (Feedback) [ATM Example]

Characteristics of System:

  1. Organization: Parts arranged in a structured order.
  2. Interaction: Parts communicate and work with each other.
  3. Interdependence: Parts depend on each other to function.
  4. Integration: All parts function together as one unit.
  5. Central Objective: Every system has a defined purpose/goal.
  6. Boundary: Line separating system from external environment.

Types of Systems:

TypeDefinitionExample

DeterministicSame input → same output alwaysCalculator (2+2=4 always)
ProbabilisticSame input → uncertain outputWeather forecast

NaturalExists in natureSolar system, Ecosystem
🏠 Example: ATM Machine is a Physical + Man-made + Open + Deterministic system. It interacts with bank servers (open), always gives correct cash for correct PIN (deterministic).
✅ Conclusion: SAD is needed to build correct, efficient, cost-effective IS on time. Without SAD → requirements misunderstood → project fails → money wasted.
📘 Definition: JAD (Joint Application Development) is a structured group workshop approach where end users, managers, and IT analysts collaborate intensively (1–5 days) to define requirements and design the system TOGETHER. A trained Facilitator guides the session.

JAD Participants:

  1. End Users: Know business needs firsthand.
  2. Business Managers: Provide priorities and business context.
  3. IT Analysts: Understand technical possibilities.
  4. Facilitator: Neutral guide who manages the session.
  5. Scribe: Documents all decisions in real-time.

JAD vs Traditional Analysis:

FeatureTraditional AnalysisJAD Workshop
MethodOne-on-one interviewsGroup intensive sessions
TimeWeeks to months1–5 day workshops
ConflictsDiscovered lateResolved immediately
OwnershipIndividual viewsShared group decisions
DocumentationAfter interviewsReal-time in session

Benefits of JAD:

  1. All stakeholders present → immediate conflict resolution.
  2. One session replaces weeks of individual interviews.
  3. Shared ownership → everyone agrees on decisions.
  4. Higher user satisfaction — users actively participate.
  5. Better requirements → fewer revisions during development.
🏠 Example: A bank needs new online banking system. JAD: Branch manager + customers + IT team + security expert sit together for 3 days and design the system collaboratively.
✅ Conclusion: JAD = Join And Decide together. Faster, better requirements, higher user satisfaction than traditional approach.

📘 Definition: Users are persons who interact with or benefit from an Information System. Different user levels have different information needs.

Four Types of Users:

  1. End Users (Operational): Daily users — data entry, transactions. Example: Bank tellers, cashiers.
  2. Operational Users: Handle operational data and reports. Example: Branch supervisors.

Six Roles of System Analyst (CCIACL):

  1. Consultant: Provides expert IS advice to management.
  2. Change Agent: Identifies need for change, helps users adapt.
  3. Investigator: Studies and documents current system problems.
  4. Architect: Creates logical and physical system design.
  5. Coordinator: Links users, developers, and management.

📘 Definition: System Analyst is an IT professional who acts as BRIDGE between business users and technical developers. Business knows WHAT they need; IT knows HOW to build; Analyst translates between both to ensure the RIGHT system is built efficiently.

Why Businesses Need System Analysts:

  1. Business users cannot write technical specifications.
  2. IT professionals don't understand business workflows.
  3. Without analyst → wrong system built → money and time wasted.
  4. Analyst prevents expensive mistakes and manages project complexity.

Six Roles (CCIACL):

  1. Consultant: Expert IS advice and recommendations to management.
  2. Change Agent: Identifies and manages organizational change from new systems.
  3. Investigator: Studies and documents current system problems.
  4. Architect: Creates logical and physical system design (DFD, ER).
  5. Coordinator: Links users, developers, and management together.
  6. Liaison: Translates technical language ↔ business language.

11 Duties of System Analyst:

  1. Investigate existing system — understand current processes.
  2. Collect requirements using interviews, questionnaires, observation.
  3. Analyze collected information and identify problems.
  4. Prepare SRS (System Requirements Specification).
  5. Design system — DFD, ER Diagram, logical and physical design.
  6. Evaluate hardware and software alternatives.
  7. Prepare Cost-Benefit Analysis and present to management.
  8. Coordinate and supervise development team.
  9. Prepare test plans and test the system.
  10. Train end users — conduct training sessions.
  11. Prepare all documentation — user manual, technical manual.

📘 Definition: Participatory Design (PD) is an approach where end users are ACTIVE CO-DESIGNERS throughout the entire design process — not just information sources. Originated in Scandinavia (1970s).

PD vs Traditional:

  • Traditional: Analyst designs → shows to users → users comment.
  • PD: Users and analyst design TOGETHER from the beginning.

Benefits:

  1. System fits ACTUAL work practices — not analyst's assumptions.
  2. High user acceptance — "WE built this together!"
  3. Reduced training time — users already familiar.
  4. Better quality — real problems solved.
Challenge: Time-consuming, needs skilled facilitation.
✅ Trick: PD = People Designing their own system! Users = Co-designers, NOT informants.

📘 Definition: SDLC (System Development Life Cycle) is a structured, phase-by-phase process for planning, creating, testing, and deploying information systems. It ensures quality, cost control, and timely delivery. SDLC is CYCLIC — maintenance may trigger a new development cycle.
┌─────────────────────────────────────────────────────────────┐ │ SDLC LIFE CYCLE │ │ ┌────────────┐ ┌────────────┐ ┌──────────────────┐ │ │ │ 1.PLANNING │───▶│ 2.ANALYSIS │───▶│ 3.LOGICAL DESIGN │ │ │ │ Feasibility │ │ SRS + DFDs │ │ DFD+ER+DD │ │ │ └────────────┘ └────────────┘ └────────┬─────────┘ │ │ ▲ │ │ │ │ ▼ │ │ ┌──────────────┐ ┌─────────────┐ ┌──────────────────┐ │ │ │ 6.MAINTENANCE │◀─│ 5.IMPLEMENT │◀─│ 4.PHYSICAL DESIGN│ │ │ │ CAPP types │ │Code+Test+ │ │ DB+UI+Hardware │ │ │ └──────────────┘ │ Train+Deploy│ └──────────────────┘ │ │ └─────────────┘ │ └─────────────────────────────────────────────────────────────┘

Phase 1 — PLANNING:

  • Identify project need. Conduct Feasibility Study (TOELS).
  • Plan resources, budget, and project timeline.
  • Output: Project Charter + Feasibility Report.

Phase 2 — ANALYSIS:

  • Study existing system. Gather user requirements.
  • Create DFD of current system. Write and get SRS approved.
  • Output: SRS Document.

Phase 3 — LOGICAL DESIGN:

  • Design WHAT system will do — technology-independent.
  • Create DFD Level 1+, ER Diagram, Data Dictionary.
  • Reviewed by USERS. Output: Logical Design Document.

Phase 4 — PHYSICAL DESIGN:

  • Design HOW system will be built — technology-specific.
  • Choose DBMS (MySQL), language (Java), hardware.
  • Reviewed by TECHNICAL TEAM. Output: Physical Design Specification.

Phase 5 — IMPLEMENTATION:

  • Code the system. Test (Unit→Integration→System→UAT).
  • Train users. Convert data. Deploy system.
  • Changeover types: Direct, Parallel, Phased, Pilot.
  • Output: Working System + User Manual.

Phase 6 — MAINTENANCE:

  • Corrective: Fix bugs after deployment.
  • Adaptive: Modify for environment changes (new laws, new OS).
  • Perfective: Add new features, improve performance.
  • Preventive: Changes to prevent future problems.
  • Output: Updated System + Maintenance Reports.
PhaseKey ActivityDeliverable
PlanningFeasibility studyProject Charter, Feasibility Report

Physical DesignDB schema, UI designPhysical Design Specification

✅ Memory Trick: PALDIM = Plan, Analyze, Logical, Design, Implement, Maintain. CAPP = Corrective, Adaptive, Perfective, Preventive (maintenance types).

📘 Definition: SRS (System Requirements Specification) is a formal document describing WHAT the system must do. It is the official CONTRACT between users and developers. Users sign it after review.

Contents of SRS:

  1. Introduction: Purpose, scope, definitions.
  2. Functional Requirements: Specific features system SHALL do.
  3. Non-functional Requirements: Performance, security, reliability.
  4. Constraints: Hardware/software/budget limitations.
  5. External Interfaces: How system connects to other systems.
  6. Acceptance Criteria: Conditions confirming system is complete.
✅ Conclusion: SRS = WHAT system must do. Users sign it. Basis for all design, development, testing, and acceptance.
📘 Definition: Documentation = systematically recording ALL information about a system throughout its entire lifecycle. Golden Rule: "If it is not documented, it does not exist."

Why Documentation is Needed:

  1. Knowledge Transfer: If developer leaves, new person can continue.
  2. Maintenance: Future developers can understand and modify system.
  3. User Training: Users need guides to operate system correctly.
  4. Legal Compliance: Contracts, audits, regulations need documented evidence.
  5. Quality: Ensures standards followed at every development stage.
✅ 5 Cs of Good Documentation: Clear, Consistent, Complete, Correct, Current (up-to-date).

📘 Definition: CBA compares total costs of system development against total expected benefits to determine financial viability. Proceed only if Net Benefit > 0.
📐 Three Key Formulas:
1. Net Benefit = Total Benefits − Total Costs (must be POSITIVE ✅)
2. Payback Period = Total Investment ÷ Annual Net Savings
3. ROI (%) = (Net Benefit ÷ Total Cost) × 100

Example:

College Fee Portal: Investment = Rs 8 lakh | Annual savings = Rs 4 lakh

Payback = 8 ÷ 4 = 2 years | ROI = (4÷8)×100 = 50% per year → Decision: PROCEED ✅

✅ Conclusion: CBA: Net=B−C | Payback=I÷S | ROI=(Net÷Cost)×100. Positive ROI = Project is economically feasible.
📘 Definition: Fact-Finding Techniques are methods used by analysts to collect information about existing systems and user requirements. Best practice: Use MULTIPLE techniques for complete picture.

Six Techniques (I-Q-O-D-G-S):

  1. Interview: Face-to-face questioning. Rich data but time-consuming.
  2. Questionnaire: Written surveys for many users. Cheap but low response.
  3. Observation: Watch actual work. Reveals real behavior.
  4. Document Review: Study existing forms, reports, manuals.
  5. Group Discussion / JAD: Multiple stakeholders together.
  6. Site Visits: Visit similar organizations for benchmarking.
✅ Trick: I-Q-O-D-G-S = Interview, Questionnaire, Observation, Document, Group, Site visit.
📘 Definition: Feasibility Study is a pre-project evaluation conducted BEFORE committing full resources, to determine if the proposed system is practical, affordable, and worth developing. Output: Feasibility Report with Go/No-Go recommendation.

Why Feasibility Study is Essential:

  1. Prevents wasting money on impractical projects.
  2. Identifies problems early — when cheap to fix.
  3. Provides management with evidence-based decision support.
  4. Reduces risk of project failure due to unforeseen constraints.

Issues Involved in Feasibility Study:

  • Lack of accurate initial information.
  • Resistance to change from users and staff.
  • High initial cost before returns.
  • Uncertainty of future benefits.
  • Time constraints — deadline may be unrealistic.

📘 Decision Table Definition: Tabular representation showing ALL possible condition combinations and their corresponding actions. Ensures no combination is missed.
📘 Decision Tree Definition: Graphical tree showing conditions as branches and actions as leaves. Same logic as Decision Table — different visual format.

Decision Table Structure:

  • Condition Stubs: List of all conditions (top-left).
  • Condition Entries: Y (True) or N (False) for each rule (top-right).
  • Action Stubs: List of all possible actions (bottom-left).
  • Action Entries: X = action taken for that rule (bottom-right).
  • Each COLUMN = one complete business rule.
  • 2 conditions → 4 rules (2²). 3 conditions → 8 rules (2³).

📘 Definition: Audit = Systematic, independent examination and evaluation of computer systems, operations, and records to verify accuracy, security, and compliance with policies and laws.

8 Objectives of Computer System Audit:

  1. Verify data accuracy, completeness, and integrity.
  2. Ensure security — check access controls prevent unauthorized access.
  3. Detect fraud — identify unauthorized or fraudulent transactions.
  4. Detect errors — find processing mistakes in systems.
  5. Check legal compliance — IT Act, data privacy, industry regulations.
  6. Evaluate efficiency — assess system performance.
  7. Review backup — ensure data backups are adequate.
  8. Recommend improvements — suggest better controls.
✅ CIA Triad: Confidentiality + Integrity + Availability = 3 pillars of computer security.

📘 Definition: Form = Structured INPUT document to collect data FROM users INTO system. Report = Formatted OUTPUT document presenting processed information FROM system TO users. Simple rule: Form = Fill In (Input). Report = Read Out (Output).

Types of Forms:

  1. Paper Forms: Physical printed forms filled by hand (offline).
  2. Electronic Forms: Screen-based forms in software applications.
  3. Web Forms: Online forms on websites and mobile apps.
  4. Turnaround Documents: Sent out, filled, and returned (feedback forms).

Types of Reports:

  1. Scheduled Reports: Generated at fixed intervals (daily, weekly, monthly).
  2. Exception Reports: Generated ONLY when something unusual occurs.
  3. On-demand Reports: Generated when specifically requested.
  4. Summary Reports: High-level totals and overview.
  5. Detail Reports: Complete line-by-line data.

Guidelines for Good FORM Design (8 Points):

  1. Meaningful Title: Clear heading identifying form purpose.
  2. Clear Labels: Every field clearly labeled — user knows what to enter.
  3. Logical Sequence: Related fields grouped together in logical order.
  4. Adequate Space: Enough room to write or type the required data.
  5. Instructions: Guidance for complex or non-obvious fields.
  6. Minimal Fields: Collect ONLY what is absolutely necessary.
  7. Validation Rules: Prevent incorrect data entry with checks.
  8. Professional Appearance: Consistent with organization branding.

Criteria for Good REPORT Design:

  • Relevance: Include only information needed by the reader.
  • Accuracy: Data must be correct and verified.
  • Timeliness: Delivered at the right time for decision-making.
  • Clarity: Easy to read and understand at a glance.
  • Completeness: All necessary information included.
