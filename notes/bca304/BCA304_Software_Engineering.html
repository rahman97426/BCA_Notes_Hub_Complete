Definition: Prototype model is an iterative approach where a preliminary working version (prototype) is built quickly to gather user feedback before full development begins.

When Beneficial:

1. When requirements are unclear or incomplete and users cannot define them precisely.

2. When new/unproven technology is being used and feasibility is uncertain.

3. When the system needs high user interaction — UI-heavy apps, games.

4. When high-risk elements need to be validated early before full investment.

Process: Gather basics → Build prototype → Show user → Get feedback → Refine → Repeat → Final system.

Advantage: Reduces misunderstanding. Finds errors early when cheap to fix.

Disadvantage: Can lead to scope creep and poor code structure if prototype code is reused.

LOC Shortcomings:

1. Language dependent — same work needs more lines in C++ than Python. Unfair comparison.

2. Available only after coding — cannot estimate project size in planning phase.

3. Penalizes efficient programmers — 100 lines may do more than 1000 lines.

4. Programmer style varies — compact vs verbose coding — no consistency.

5. Does not reflect functionality — more lines ≠ more useful software.

6. Counting method varies — blank lines, comments counted or not?

Alternative: Function Points (FP) overcome these — language-independent, measures user functionality.

Software Crisis (1960s–70s): Series of serious problems that affected the software industry.

Problems:

1. Projects delivered very late — months or years behind schedule.

2. Projects exceeded budgets — sometimes by 100% or more.

3. Software was unreliable — full of bugs, crashed frequently.

4. Code was very hard to maintain — poor documentation, no structure.

5. Software did NOT meet user needs — wrong system was built.

How SE Solved It:

1. Introduced systematic SDLC phases — Planning, Analysis, Design, Testing.

2. Defined formal lifecycle models — Waterfall, Prototype, Spiral.

IEEE defined SE: "Systematic, disciplined, quantifiable approach to software development."

Process Metrics: Measure efficiency of the development process itself.

1. Defect Removal Efficiency = (Defects found before delivery ÷ Total defects) × 100%

2. Effort Variance = Actual effort − Estimated effort

3. Schedule Variance = Actual time − Planned time

Product Metrics: Measure characteristics of the software product itself.

1. Size Metrics — Lines of Code (LOC), Function Points (FP)

2. Complexity Metrics — Cyclomatic complexity, nesting depth

3. Quality Metrics — Reliability score, maintainability index, usability ratings

Key Rule: "You cannot control what you cannot measure." — Metrics are essential for project management.

Introduction: Waterfall Model is the oldest and most known software development model. It follows a linear sequential approach — each phase must be completed fully before the next begins.

Definition: A linear sequential development process where phases flow downward (like a waterfall) with minimal backward movement between phases.

 

Six Phases:

1. Requirements Gathering — Document ALL user requirements completely. Output: SRS Document.

2. System Design — Architecture, data structures, interfaces, algorithms. Output: Design Document.

3. Implementation (Coding) — Developers write code based on design. Output: Software modules.

4. Testing — Unit, Integration, System, UAT testing. Output: Test Reports.

5. Deployment — Release to production environment. Output: Live system.

6. Maintenance — Bug fixes, updates, enhancements. Output: Updated system.

 

📐 DIAGRAM — WATERFALL MODEL:

Requirements → System Design → Implementation → Testing → Deployment → Maintenance

↓ ↓ ↓ ↓ ↓ ↓

SRS Document Design Doc Source Code Test Report Live System Updated System

 

Advantages:

1. Simple and easy to understand — linear, logical flow.

2. Clear documentation at each phase.

3. Well-suited for small projects with stable requirements.

4. Structured and predictable timeline.

 

Disadvantages:

1. Rigid and inflexible — changing requirements is very expensive.

2. Late detection of defects — testing happens at the end.

3. No working software until late — stakeholders cannot see progress.

4. High risk at end — if requirements were wrong, entire project may fail.

 

When to Use:

1. Requirements are clear, stable, and well-documented.

2. Project is small to medium in size.

3. Technology is well-understood by the team.

 

Conclusion: Waterfall is simple and disciplined but too rigid for modern projects. For evolving requirements, Spiral or Agile models are preferred.

Introduction: Spiral Model, proposed by Barry Boehm in 1986, is a risk-driven iterative model combining Waterfall's structure with Prototyping's flexibility. Every cycle explicitly focuses on risk analysis.

Definition: A risk-driven iterative model where each spiral cycle passes through 4 quadrants: Planning → Risk Analysis → Development → Evaluation.

 

Four Quadrants of Each Spiral Cycle:

1. Planning (Objectives): Define objectives, alternatives, constraints for current iteration.

2. Risk Analysis: Identify, analyze, prioritize risks. Build prototypes to resolve high-risk areas.

3. Development & Testing: Develop the product for current iteration. Test to verify correctness.

4. Evaluation & Review: Customer evaluates output. Plans for next iteration based on feedback.

 

📐 DIAGRAM — SPIRAL MODEL:

PLANNING | RISK ANALYSIS

Define objectives | Identify & resolve risks

─────────────────────────────────────────────

EVALUATION & REVIEW | DEVELOPMENT & TESTING

Customer reviews output | Code, test, integrate

Plan next iteration | Produce working build

 

Risk Management in Spiral:

1. Risk is explicitly identified at start of EVERY cycle.

2. Prototypes built to address high-risk unclear requirements early.

3. If risk too high, project can be stopped — saving resources.

 

Waterfall vs Spiral:

• Waterfall: sequential, rigid, ONE pass. | Spiral: iterative, flexible, MULTIPLE cycles.

• Waterfall: risk found late. | Spiral: risk analyzed every cycle.

• Waterfall: for stable projects. | Spiral: for large complex risky projects.

 

Advantages: Flexible, risk-focused, customer involvement every iteration.

Disadvantages: Expensive, complex to manage, needs skilled risk analysts.

 

Conclusion: Spiral model is ideal for large, complex, high-risk projects where risk management is critical to project success.

Delphi technique for cost estimation involves:

Definition: Delphi is a group estimation technique where multiple experts give independent cost estimates anonymously in multiple rounds until consensus is reached.

Process (3 Rounds):

1. Round 1: Each expert submits estimate privately — no group discussion, no peer influence.

2. Round 2: Average results shared anonymously. Experts revise estimates seeing others' responses.

3. Repeat: Continue until experts mostly agree (consensus).

Why it works: No one feels pressure to match boss or loudest person. Independent thinking leads to accurate estimates.

Advantages: Reduces bias, documents reasoning, valuable for novel projects with no historical data.

Disadvantages: Time-consuming (2-4 weeks), needs skilled facilitator, expert availability required.

SRS = System Requirements Specification — formal contract between users and developers describing WHAT system must do.

6 Key Characteristics:

1. Correct: Every requirement accurately reflects actual user needs.

2. Unambiguous: Each requirement has ONLY ONE possible interpretation.

3. Complete: ALL functional and non-functional requirements included — nothing missing.

4. Consistent: No contradictions between any two requirements.

5. Verifiable: Each requirement can be tested cost-effectively — measurable criteria stated.

6. Modifiable: SRS can be updated easily while maintaining consistency.

IEEE 830 Structure: Section 1 (Introduction) → Section 2 (Overall Description) → Section 3 (Specific Requirements)

LOC (Lines of Code):

• Counts executable source code statements

• Language dependent — same code = more lines in C++ vs Python

• Available only AFTER design/coding phase

• Disadvantage: penalizes efficient programmers writing less code

 

Function Points (FP):

• Counts user-visible functionality: Inputs + Outputs + Inquiries + Files + Interfaces

• Language INDEPENDENT — same FP count regardless of language

• Available EARLY — can estimate at requirements phase

• Advantage: measures from USER perspective, not technical view

 

Key Difference: LOC = WHAT was written. FP = WHAT the user gets. FP is more accurate for early estimation.

Functional Requirements — WHAT the system must DO:

• System shall allow user login with username and password

• System shall calculate invoice including applicable taxes

• System shall send SMS alert when stock falls below minimum level

 

Non-Functional Requirements — HOW WELL the system performs:

• Performance: System shall respond to any query within 2 seconds

• Reliability: System shall have 99.9% uptime — max 9 hours downtime/year

• Security: All data shall be encrypted using AES-256 standard

• Usability: New users shall complete basic task in 10 minutes without training

 

Key Difference: Functional = features and behavior. Non-functional = quality attributes and constraints.

Introduction: COCOMO (Constructive Cost Model) by Barry Boehm (1981) provides empirically-validated formulas to estimate software project effort and schedule based on size.

 

Basic COCOMO Formula:

Effort (Person-Months) = a × (KLOC) ^ b

Duration (Months) = c × (Effort) ^ d

 

Three Project Categories:

1. ORGANIC — Small team, familiar tech, relaxed environment

Formula: Effort = 2.4 × (KLOC)^1.05 | Duration = 2.5 × (Effort)^0.38

Example: Payroll system, inventory system

 

2. SEMIDETACHED — Medium team, mixed experience, moderate constraints

Formula: Effort = 3.0 × (KLOC)^1.12 | Duration = 2.5 × (Effort)^0.35

Example: Database management system, compiler

 

3. EMBEDDED — Real-time, tight hardware/software constraints, strict deadlines

Formula: Effort = 3.6 × (KLOC)^1.20 | Duration = 2.5 × (Effort)^0.32

Example: Flight control system, nuclear reactor control

 

Worked Example (Semidetached — 50 KLOC):

Step 1: Effort = 3.0 × (50)^1.12 = 3.0 × 56.7 = 170 person-months

Step 2: Duration = 2.5 × (170)^0.35 ≈ 2.5 × 7.2 ≈ 18 months

Step 3: Team Size ≈ 170 ÷ 18 ≈ 9–10 developers

 

Advantages:

1. Empirically validated against 63 real projects.

2. Consistent and reproducible — same inputs, same estimate.

3. Accommodates different project complexity levels.

 

Limitations:

1. Accuracy depends on correct KLOC estimation.

2. Less accurate for novel projects with no historical data.

3. Static coefficients may not reflect modern development practices.

 

Conclusion: COCOMO provides a systematic mathematical basis for cost estimation. For better accuracy, use Intermediate COCOMO which adds 15 cost driver multipliers.

DFD (Data Flow Diagram):

• Shows how DATA flows between system processes

• System-level view — models WHAT system does

• No decision boxes, loops, or timing shown

• Used in: System analysis and logical design phase

• Symbols: Circle(process), Arrow(flow), Open-box(store), Rectangle(entity)

 

Flowchart:

• Shows sequence of LOGIC steps and control flow

• Module-level view — models HOW it works internally

• Decision boxes (diamonds), loops, timing shown

• Used in: Detailed program design and coding phase

• Symbols: Rectangle(process), Diamond(decision), Oval(start/end)

 

Key Difference: DFD = WHAT data is transformed. Flowchart = HOW algorithm/logic works.

FOD (Function-Oriented Design):

• System viewed as set of FUNCTIONS

• Data shared globally across functions

• Top-Down approach — decomposition

• Tools: DFD + Structure Charts

• Best for: stable, procedural, computation-heavy systems

 

OOD (Object-Oriented Design):

• System viewed as set of OBJECTS (data + behavior together)

• Data encapsulated inside objects — hidden from outside

• Bottom-Up approach — composition

• Tools: UML — Class Diagram, Sequence Diagram

• Best for: complex, evolving, large-scale systems

 

4 OOD Principles: Abstraction | Encapsulation | Inheritance | Polymorphism

Balancing DFD Definition: Ensuring data flows entering/leaving a process in Level N DFD exactly match the data flows in its expanded Level N+1 DFD.

 

Balancing Rule: Inputs and outputs of a process at Level N = Inputs and outputs of same process at Level N+1.

 

Example:

Level 0: [Customer] → 'Order' → (ORDER SYSTEM) → 'Invoice' → [Customer]

Level 1 MUST still show: receives 'Order' from [Customer] and produces 'Invoice' to [Customer]

Level 1 expansion shows: (1.0 Validate Order) → (2.0 Process) → (3.0 Generate Invoice)

External flows 'Order' in and 'Invoice' out are PRESERVED — Balanced ✓

 

Unbalanced: If Level 1 shows a new external flow 'Payment' that Level 0 doesn't have — ERROR.

Why Important: Unbalanced DFD = data mysteriously appears/disappears = design inconsistency error.

4 Core OOD Principles:

 

1. Abstraction: Hide complex implementation details, expose only essential features.

Example: Driver uses car.start() without knowing engine mechanics.

 

2. Encapsulation: Bundle data + methods in one unit (object). Restrict direct access.

Example: Bank account balance hidden — only accessible via deposit() and withdraw().

 

3. Inheritance: Child class acquires properties and methods of parent class.

Example: Sparrow and Pigeon inherit from Bird class — both have fly() method.

 

4. Polymorphism: One interface, multiple implementations.

Example: draw() method works for Circle, Square, Triangle — each draws differently.

Introduction: DFD (Data Flow Diagram) is a graphical representation showing how data flows through a system — what processes exist, where data is stored, and what data enters/exits the system boundary.

Definition: DFD is a structured analysis tool using four basic symbols to model the logical flow of data through a system without showing implementation details.

 

Four DFD Symbols (Gane-Sarson Notation):

1. Process (Rounded Rectangle/Circle): Transforms input to output. Named with verb phrase.

Example: 'Validate Order', 'Calculate Tax', 'Generate Report'

 

2. Data Flow (Arrow with Label): Movement of data between components.

Example: → 'Customer Name', → 'Invoice Amount', → 'Book Request'

 

3. Data Store (Open Rectangle): Repository where data rests.

Example: [= Customer Database =], [= Order File =]

 

4. External Entity (Rectangle/Square): Person or system OUTSIDE boundary.

Example: Customer, Manager, Supplier, Bank

 

Three DFD Levels:

• Level 0 — Context Diagram: Entire system = ONE process. Shows all external entities and boundary.

• Level 1 DFD: Level 0 circle expanded — shows major sub-processes, data stores, flows.

• Level 2+ DFD: Each Level 1 process further expanded into detailed sub-processes.

[Librarian] ──'Catalogue Update'──▶ (LIBRARY SYSTEM) ──'Reports'──▶ [Librarian]

DFD Rules (Must Follow):

1. Every process must have at least ONE input AND ONE output.

2. Data CANNOT flow directly between two data stores.

3. Data CANNOT flow directly between two external entities.

4. DFD must be BALANCED across levels.

 

Limitations of DFD:

1. Cannot show control flow — no loops, if-else decisions, or timing.

2. Cannot model real-time systems — no events or interrupts.

3. No error handling shown.

4. Becomes very complex for large systems.

 

Conclusion: DFD is an excellent logical analysis tool for data flow modeling. Must be leveled and balanced for consistency. Use flowcharts alongside DFDs for control flow logic.

Black-Box Testing:

• Tests functionality WITHOUT knowing internal code

• No source code knowledge required

• Performed by: Software Testers / QA Team

• Tests: Inputs vs expected outputs (requirements-based)

• Techniques: Equivalence Partitioning, Boundary Value Analysis

• Also called: Functional testing

• Level: System testing, Acceptance testing

 

White-Box Testing:

• Tests internal CODE STRUCTURE and logic paths

• Requires full source code access

• Performed by: Software Developers

• Tests: Logic paths, branches, code statements

• Techniques: Statement, Branch, and Path coverage

• Also called: Structural / Glass-box testing

• Level: Unit testing, Integration testing

Definition: Regression testing is re-testing previously working software after making changes to ensure existing functionality still works correctly.

 

When is it Done?

1. After bug fixes — ensure fix didn't break other parts.

2. After adding new features — ensure new code doesn't affect old features.

3. After code refactoring — code restructured but should behave same.

4. After environment changes — OS upgrade, new database version.

 

Why Necessary?

• A change to fix one bug can accidentally break other working features — called a 'regression'.

• Regression testing catches these unintended side effects BEFORE they reach users.

 

How Performed:

• Run SAME old test cases + NEW test cases for the specific change made.

• Often automated using tools like Selenium, JUnit, TestNG for efficiency.

Definition: Musa's Basic Execution Time Model (1975) is a software reliability model predicting failure intensity (failure rate) as a function of CPU execution time — not calendar time.

 

Core Formula:

λ(τ) = f × K × [N − μ(τ)]

 

Where:

• λ(τ) = Failure intensity (rate) at execution time τ

• f = Linear execution frequency of the program

• K = Fault exposure ratio (proportion causing failures)

• N = Total faults at start of testing

• μ(τ) = Expected failures experienced by time τ

 

Key Insight: As faults are found and fixed, failure rate DECREASES exponentially over time.

Based on: Poisson process + exponential distribution of failures over execution time.

4 Levels of Software Testing:

 

1. Unit Testing: Test individual modules/functions in isolation.

Done by: Developers | Tool: JUnit, NUnit

 

2. Integration Testing: Test how modules work TOGETHER — find interface errors.

Methods: Top-down (Stubs), Bottom-up (Drivers), Big-bang, Sandwich

 

3. System Testing: Test entire complete system against SRS requirements.

Done by: QA Team | Tests: functional, performance, security, stress

 

4. User Acceptance Testing (UAT): End users test system in real environment.

Done by: Actual users/clients | Last gate before deployment

 

Order: Unit → Integration → System → UAT → Deployment

Introduction: Software testing ensures quality and correctness. White-box (structural) and Black-box (functional) testing examine software from completely different perspectives. Modern quality assurance uses BOTH approaches.

 

PART 1 — WHITE-BOX TESTING:

Definition: Testing method where tester has complete knowledge of and access to source code, internal structure, and design. Also called Glass-box, Clear-box, or Structural testing.

 

Three White-Box Techniques:

1. Statement Coverage: Execute every executable statement at least once.

Formula: Coverage% = (Statements executed ÷ Total statements) × 100

Weakness: Simplest form — doesn't test all outcomes of conditions.

 

2. Branch Coverage (Decision Coverage): Execute every possible outcome of every decision point.

Tests BOTH TRUE and FALSE branches of every if-else and loop.

Stronger than statement coverage — catches more logic errors.

 

3. Path Coverage: Execute EVERY possible path through the code.

Most thorough — guarantees all logic is tested.

Most expensive — number of paths can grow exponentially.

 

White-Box Advantages: Thorough code coverage | Finds hidden logic errors | Measures code quality | Identifies dead code

White-Box Disadvantages: Time-consuming | Needs programming expertise | Cannot find missing requirements

 

PART 2 — BLACK-BOX TESTING:

Definition: Testing method where tester treats system as 'black box' — NO code knowledge. Only inputs and expected outputs are considered. Also called Functional testing.

 

Two Key Black-Box Techniques:

1. Equivalence Partitioning: Divide ALL inputs into partitions of valid/invalid values.

Test ONE representative value per partition.

Example — Age input (valid: 1-120):

Partition 1: <1 (invalid) | Partition 2: 1-120 (valid) | Partition 3: >120 (invalid)

Test: -5 (invalid), 50 (valid), 200 (invalid) — 3 test cases cover all possibilities.

 

2. Boundary Value Analysis (BVA): Test at the EDGES of valid input ranges.

Errors occur most often at boundary values.

Example — Same Age input (1-120):

Test: 0, 1, 2, 119, 120, 121 — (min-1, min, min+1, max-1, max, max+1)

 

Black-Box Advantages: No code knowledge needed | Tests from user perspective | Finds requirement gaps

Black-Box Disadvantages: Cannot test all internal paths | May miss logic errors

 

Comparison Summary:

• Code knowledge: White-box = Required | Black-box = Not required

• Performed by: White-box = Developers | Black-box = Testers

• Tests: White-box = Internal logic | Black-box = External behavior

• Level: White-box = Unit, Integration | Black-box = System, UAT

 

Conclusion: White-box and Black-box are COMPLEMENTARY — not competing. White-box ensures code quality; Black-box validates user requirements. Best practice: use both for comprehensive testing coverage.

1. Corrective (~21%): Fix defects/bugs found after release. REACTIVE.

Example: App crashes on login → find and fix authentication bug.

Example: Refactor messy code | Add comprehensive error logging.

ISO 9000:

• International standard for Quality Management Systems

• Focuses on: documenting and FOLLOWING defined processes

• Applies to: ANY industry (manufacturing, services, software)

• Result: Binary certification — Certified OR Not Certified

• Third-party audit required for certification (valid 3 years)

• Key principle: 'Say what you do. Do what you say. Prove it.'

 

SEI CMM:

• Framework for assessing software process MATURITY

• Focuses on: IMPROVING software process over time

• Applies to: Software organizations SPECIFICALLY

• Result: Maturity level rating 1 to 5

• Assessment-based — no formal certification

• Goal: Continuously improving process capability

 

Together: ISO for customer certification + CMM for internal improvement = best strategy.

Definition: Reverse Engineering is analyzing existing software to recreate design documents/specs when original documentation is unavailable or missing.

 

Process:

Source Code → Program Understanding → Design Recovery → Requirements Recovery

 

5 Key Uses and Significance:

1. Legacy System Maintenance: Old systems with no docs can be understood and maintained.

2. System Migration: Move old system to new platform by understanding current design.

3. Security Analysis: Analyze malware or third-party software for security vulnerabilities.

4. Component Reuse: Find reusable components in existing code for new projects.

5. Documentation Recovery: Create missing technical documentation for audits/compliance.

 

Tools: Doxygen (documentation), Understand, Rational Rose, Enterprise Architect.

Why Estimate Maintenance Costs?

Maintenance = 60-80% of total software lifecycle cost. Must plan and budget carefully.

 

Factors Increasing Maintenance Cost:

1. Poor code quality — messy, undocumented code costs more to understand and fix.

2. Missing documentation — developers waste time figuring out the system.

3. Staff turnover — new staff need time to learn system = higher cost.

4. Old/legacy systems — older code = harder and costlier to modify.

5. Frequent requirement changes — more changes = more maintenance cost.

 

Estimation Approaches:

• Rule of thumb: Annual maintenance ≈ 15-20% of original development cost per year.

• Per change request: Estimate effort per bug fix or enhancement separately.

• Function Point approach: Measure size of changes in FP, apply productivity rates.

 

Lehman's Law: Software must be continuously adapted or it becomes progressively less useful.

Introduction: Software quality assurance requires systematic standards. ISO 9000 and SEI CMM are the two most important quality frameworks used globally to ensure and improve software quality.

 

ISO 9000 — International Quality Management Standard:

Definition: ISO 9000 is a family of international standards defining requirements for a Quality Management System (QMS). It ensures consistent delivery of products meeting customer requirements.

 

Key ISO Standards:

• ISO 9001: Requirements for QMS — most important, covers production, development, servicing.

• ISO 9000: Fundamentals and vocabulary of quality management systems.

• ISO 9004: Guidelines for performance improvement beyond basic compliance.

 

ISO 9000 Principles:

1. Customer focus — primary aim is meeting customer requirements.

2. Process approach — activities managed as processes with defined inputs and outputs.

3. Continual improvement — ongoing improvement of QMS performance.

4. Evidence-based decision making — decisions based on data and facts.

SEI CMM — Capability Maturity Model:

Definition: CMM is a framework developed by Carnegie Mellon's SEI for assessing and improving the maturity of software development processes. Maturity ranges from Level 1 (chaotic) to Level 5 (optimized).

 

Five CMM Maturity Levels:

Level 1 — INITIAL:

• Ad-hoc, chaotic processes. Success depends on individuals, not process.

• No repeatable processes. Cannot predict outcomes.

 

Level 2 — REPEATABLE:

• Basic project management established.

• Requirements managed. Past successes can be repeated on similar projects.

 

Level 3 — DEFINED:

• Processes documented, standardized, and integrated ACROSS entire organization.

• Consistent approach used by all teams organization-wide.

 

Level 4 — MANAGED:

• Quantitative control of processes using statistical data and metrics.

• Variation in process performance is identified and controlled.

 

Level 5 — OPTIMIZING:

• Continuous process improvement based on quantitative feedback.

• Defect prevention through proactive identification of improvement opportunities.

 

ISO 9000 vs SEI CMM — Key Differences:

• Focus: ISO = document & follow processes | CMM = improve process maturity over time

• Industry: ISO = any industry | CMM = software organizations specifically

• Result: ISO = binary certified/not | CMM = 1-5 maturity level rating

• Approach: ISO = standards compliance | CMM = improvement journey

 

Best Strategy: Pursue BOTH — ISO for customer certification + CMM for internal improvement.

 

Conclusion: ISO 9000 ensures processes are consistently followed. SEI CMM provides a roadmap for continuous process improvement. Together they form a comprehensive quality assurance framework. Most mature organizations aim for ISO certification + CMM Level 3 or above.

Introduction: Software Maintenance is the most expensive phase of the software lifecycle, consuming 60-80% of total costs. It involves ALL modifications made AFTER delivery to correct faults, improve performance, or adapt to changing environments.

 

Definition (IEEE 1219): 'The process of modifying a software system after delivery to correct faults, improve performance, adapt to changed environment, or add new features.'

 

4 Types of Software Maintenance:

1. CORRECTIVE (~21%) — Fix defects/bugs found after release. REACTIVE.

Example: Mobile app crashes on login → investigate and fix authentication module.

 

2. ADAPTIVE (~25%) — Modify software to work in changed environment. REACTIVE.

Example: Update payroll system for new income tax slabs.

Example: Migrate from MySQL 5 to MySQL 8 — update all queries.

 

3. PERFECTIVE (~50%) — Add new features or improve performance. LARGEST portion.

Example: Add voice search feature users requested.

Example: Optimize database queries — reduce response time from 5s to 0.5s.

 

4. PREVENTIVE (~5%) — Proactive changes to prevent future failures. PROACTIVE.

Example: Refactor spaghetti code before it causes maintenance nightmare.

Example: Update SSL certificates before expiry to prevent security breach.

 

Maintenance Process Models:

1. QUICK FIX MODEL:

Apply minimum fix immediately without full analysis.

Fast but creates technical debt. Risky — fix may introduce new bugs.

 

2. ITERATIVE ENHANCEMENT MODEL (Best Practice):

Systematic: Understand system → Identify change → Design fix → Implement → Test → Deliver.

Proper analysis prevents introducing new defects.

 

3. FULL REUSE MODEL:

Identify reusable components. Redesign using existing tested assets.

Promotes code reuse and reduces duplication.

 

Reverse Engineering in Maintenance:

When original documentation is missing — analyze code to recover design specifications.

Process: Source Code → Program Understanding → Design Recovery → Documentation

Used for legacy systems that must be maintained but have no documentation.

 

Estimation of Maintenance Costs:

• Annual maintenance cost ≈ 15-20% of original development cost per year.

• Key factors raising cost: poor code quality, missing documentation, high staff turnover.

• Lehman's Laws: Software must be continuously adapted or becomes less useful over time.

• BEST SOLUTION: Plan for maintainability DURING design phase:

- Good documentation | Modular design | Clean coding standards | Proper testing

 

Conclusion: Software maintenance is inevitable and critical. Preventive and perfective maintenance — though often undervalued — are the best long-term investment in software health and reduced long-term costs.
